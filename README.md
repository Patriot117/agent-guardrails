# agent-guardrails

How I stopped an AI agent from sending email I hadn't approved, in three layers, with the limits I haven't solved yet.

This is a small, clean version of the pattern I run in my own business. My government contracting business mostly runs on an agent system I built in Claude Code. Every morning it pulls new bids, prices them with suppliers, and drafts quotes. I decide what we bid and what gets sent. This repo holds none of that system's code or data. It's the idea, rebuilt from scratch so anyone can read it in ten minutes and run it.

## The problem

Early on, when the agents first started sending email, something went out that I hadn't approved. It was embarrassing, and it made me look like an amateur.

My first fix was rules in the prompt: never send without approval. The model ignored them. In my experience, the longer a prompt gets, the more the agent decides for itself which rules to take seriously, a version of what people call context rot. A rule in a prompt is a suggestion.

So I set one goal: make it structurally impossible for the system to do what I don't want, not just unlikely.

## Three layers

**1. The prompt sets the focus.** It's still useful for telling the agent what the job is. It's just not where the hard rules live.

**2. Hooks are fail-closed gates.** Claude Code runs a hook before every tool call. [`hooks/send_gate.py`](hooks/send_gate.py) looks at the call and gives a yes-or-no answer. A send goes through only if every recipient has a line in `approvals.txt`, a file a human writes. Any shell command that names the send script, the approval file or the gate's own files has to take a plain shape: a read (`cat`, `grep`, `ls` and a few others, piped together if you like), `python3 examples/send_email.py` with flags the gate knows, or a few git commands like `git diff` and `git commit`. No `$`, backticks, redirects, `;`, `&` or parentheses. Wrappers like `timeout`, interpreter flags and pipes into a send are refused, even for an approved recipient. That's an allowlist, and it's on purpose: the first version tried to understand shell syntax, and a reviewer got sends past it a dozen ways. Shell is too big to out-think, so the gate refuses what it can't fully read. Commands with a word the shell expands into other names, like a glob, a `{a,b}` brace or `$'...'` quoting, or with a letter outside ASCII (a Mac disk opens `ſend_email.py` as the real file), can only be a plain read or git, whatever they name. That includes the patterns zsh (the Mac default) and bash's extglob add: groups like `send_emai(l).py`, number ranges like `<1-9>`, and zsh's extended `^`, `~` and `x#`. `$''` and `$""` count anywhere, even inside quotes. A quoted glob only gets a pass on a single plain line: once a command has a `#`, a backtick, `$(`, `${`, a heredoc, a second line, a `$` outside single quotes, or hands text to another shell (`eval`, `bash -c`, `watch`, `ssh`, however the name is quoted), the gate can't be sure what the shell treats as quoted, so every one of those pattern characters counts, quoted or not. A read can't send or write, so it doesn't matter what the pattern turns into. If the gate's own logic hits an error, it blocks. The shipped settings run the hook on every tool, and with `python3 -I`, so a file the agent drops next to the hook (a fake `json.py`) can't load inside it.

[`checks/outbound_checks.py`](checks/outbound_checks.py) holds the other yes-or-no rules: no unfilled placeholders, attachments actually attached, no em dashes in what a buyer reads. The sender runs these itself, so a send the hook allows still has to pass them. If a rule can be written as code, it shouldn't be left to a model to remember.

**3. Adversarial review agents check what got through.** [`.claude/agents/reviewer.md`](.claude/agents/reviewer.md) is an agent with one short objective: find what's wrong with another agent's work. It can read files but can't edit or send, so the author and the reviewer are never the same agent. That's separation of duties, and it's my answer to the long prompt. A specialist with one job and nothing else to worry about stays on task and does that job well.

## Two design choices that matter more than they look

**Don't cry wolf.** The hard part isn't catching sends. It's not catching everything else. If the gate fires every time the agent reads the send script or runs the tests, I learn to click approve without reading, and a gate that's always approved is worse than none because it feels like protection. So plain reads pass: `grep smtp send_email.py` and `cat approvals.txt` go straight through, and so do `git add`, `git diff` and `git commit` on the send script. Dry runs pass, because they never transmit and they keep rehearsal frictionless. The allowlist has a cost I chose to pay: anything else that names the send script, like `sed -n 1,20p send_email.py`, is refused, and so is a read with a `$`, parentheses or `||` in it, or a real send with `2>&1` on the end or a `$` or `&` in its subject. So is a glob or brace outside a read or the git commands above, like `pytest tests/*`, `rm build/*` or `git reset HEAD~1`, any command with a non-ASCII letter that isn't a read, and anything besides a read or git where `hooks` or `checks` ends a word or runs into a dot or dash, or that names `.claude`, `site-packages` or a `.pth` or `sitecustomize` file, like `cd .claude`, `gh pr checks 12`, `pytest tests/test_checks.py`, `python3 webhooks.py` or `pytest -k sitecustomize`, and any of those with a backslash at the end of a line, or with an unmatched quote anywhere, even in a comment like `# it's`. That last rule covers reads and git too: `cat approvals.txt # it's` is refused. So is any command with `$''` or `$""` in it, and anything besides a read or git that has a `*`, `?`, `^`, `[..]` or `{a,b}` anywhere, even in quotes or a comment, once it also has a `#`, a backtick, `$(`, `${`, a heredoc, a second line, a `$` outside single quotes or `eval`/`bash -c`, like `python3 -c "print(2*3)" # check`, `bash -c 'ls *.txt'` or `find . -name "*.py" -newer "$REF"`. Parentheses and a `#` right after a letter count as pattern characters there too, which catches more than it sounds like: a heredoc commit message with `fix(x):` in it, a URL with a `#fragment`, or `python3 -c "print(1)" # x`. The shell names are looked for anywhere in the command, even inside quoted text, so `gh issue create --title "Fix the deploy script" --body "Why does it fail?"` is refused too. If it also has a `$`, a backtick, parentheses or a second line, a read or git is refused too, like `grep -rn "a.*b" $(git ls-files)`. Unquoted parentheses that aren't a `$(...)`, like `(cd build && make)`, and a `^` or a `~` inside a word outside a read or git, like `npm i foo@^1.2`, are refused for the same reason. An MCP read whose name has a write word in it, like `get_settings`, is refused when it names a protected file. A shell whose working folder is inside a `.claude` folder can only read. That includes the setup line below, so run it yourself rather than asking the agent to. Those get rewritten, not waved through.

**Protect the approval record, and the gate itself.** If the agent can write its own approvals, the gate is decoration, and the same goes for a gate it can switch off. The hook blocks the agent's file tools on `approvals.txt`, `send_gate.py`, `send_email.py` and `checks/outbound_checks.py`, anything in `hooks/`, `checks/` or any `.claude/` folder, your own `~/.claude` included, since user settings can switch hooks off too (that covers the settings and the reviewer's own definition), and Python's startup files, any MCP tool that names one of them and isn't a pure read, and any shell command that names one of them and isn't a plain read or a safe git command. Reading and committing are fine. All of that is reading command text, so treat it as a tripwire. The lock is file ownership: have another account own the gate's files, like `sudo chown -R root hooks checks approvals.txt .claude`, and the agent can't write inside them whatever it types (it can still move or delete them through the folder they sit in, which only the tripwire covers). You then edit approvals with `sudo`.

## What isn't solved

This is the part I care most about.

- **The gate only sees names it can read.** A command that builds the name at runtime, like a variable that holds `send_email.py` or the `ail` in it, gets past it. (A variable that's probably empty, glued inside a spelled-out name like `send_em${X}ail.py`, is caught.) So does a pattern a program matches for itself rather than the shell, like Python's `glob` or `find -name`, and a program that starts its own shell on text you hand it, like `python3 -c "import os; os.system('...')"`, `make` or `npm run`: the gate knows the common shells, `eval` and a few others, not every program that calls one. zsh options that are off by default and that the gate doesn't model, like `braceccl` (which makes `send_emai{l}.py` a pattern), would open more spellings, so leave them off. So does anything the agent writes for itself that calls the sender later: its own script, a test file, a git hook that fires on the next `git commit`. MCP sends are caught by the words send, reply or forward in the tool's name, so a tool that delivers mail under another name, or shares a file or sends a calendar invite, isn't. Sends whose recipients the gate can't see, like sending a saved draft or replying to all, are refused rather than guessed at. That's the line between this hook and a real sandbox, which would take the network away instead of reading commands.
- **The approval file isn't a lock.** For the same reason, a write that never spells out the name isn't caught: copying a whole folder over `approvals.txt` or the hook, a `find -exec` or `rsync --include` pattern that matches it, moving `.claude/` aside so the hook stops loading, `git checkout .`, a name built at runtime. The sender is an ordinary script, so a module the agent plants next to it or at the top of the repo (a fake `json.py`) can change what it does; the hook's recipient check still runs before it. An MCP tool counts as a read when its name starts with a word like `get` or `list` and has no write word in it, so a writing tool named like a read (`searchandoverwrite`, or a verb the list doesn't have) gets past. What it buys is that a self-approval can't be quiet: it has to get past the hook, then the reviewer, then show up in a file I read. In my own system that file is tracked in git and each approval is single-use, moved to a closed list once the send is verified. That turns an invisible failure into a loud one. It doesn't make it impossible.
- **The hook has to start to protect anything.** If `python3` is missing or the script has a syntax error, Claude Code treats that as a hook error and lets the call through. Fail-closed covers errors inside the gate's logic, not a gate that never runs. Python runs `.pth` and `sitecustomize` files at startup even under `-I`, and a broken one crashes the hook the same way. The gate refuses writes that name them or `site-packages`, but a package the agent installs can carry one without naming it, and the hook runs whichever `python3` comes first on the PATH, so point the settings at an interpreter the agent can't write to. Run the tests after every change to it.
- **Checkers can share blind spots.** If the reviewer runs on the same model as the author, stacking more reviewers may not help as much as it looks. I don't know yet how many layers it takes or when they stop adding anything.
- **Not everything reduces to code.** "Is this price right" or "does this answer what the buyer asked" still needs judgment. The open question is how much of that judgment can be pushed down into deterministic checks over time.

The gate in my own system has grown to about 4,900 lines, almost all of it edge cases that came up in real use. While building this repo, another guard in that system blocked me from writing this repo's `.claude/settings.json`, because it treats any write to a hook config as a guard rewriting itself. That's why the settings file ships as [`examples/settings.json`](examples/settings.json) and you copy it in yourself. It's the same idea working the way it should.

This repo got the same treatment, seventeen times. A review agent that hadn't seen the code went after the first version and found six ways past the gate, including a second line in the same command, a `timeout` prefix, and a Gmail tool name the matcher missed. I patched each one. The second round found the patches had opened new holes: a `#` that the parser read as a comment but the shell didn't, a send script piped into `python3 -`, `xargs`, and globs. Patching shapes one at a time wasn't converging, so I threw that approach out and rebuilt the gate as the allowlist above. The third round still got through: `git grep -O` runs any command you give it, and I'd put `git grep` on the safe list, and MCP mail tools that nest recipients under unusual keys hid them from the check. The fourth round went after spelling: `send_emai{l..l}.py`, `[^x]` globs, a long s (ſ) that a Mac disk opens as a plain s, and the fact that nothing stopped the agent from editing the gate itself. I patched those by working out what each pattern could spell, and the fifth round beat that the same way the second round beat the first gate: `[[:alpha:]]` classes, nested braces, a `/` inside a brace, and a fake `shlex.py` dropped next to the hook. So I stopped guessing. Any command the shell would expand can only be a read or git now, which is safe no matter what it expands to. The sixth round found that fix had opened one hole of its own: copying a settings file into `.claude/` by folder name, which can switch the hook off. That's closed too. The seventh found I was still guarding files, not folders: a planted `checks/__init__.py` runs inside the sender, and the reviewer's own definition in `.claude/agents/` was writable. Whole folders are guarded now. The eighth glued the folder name onto an option, `tar -Chooks`, and overwrote the gate itself. That's caught now too, but eight rounds of new spellings is the lesson: a check that reads commands is a tripwire, and the lock is who owns the files, which is why the section above says to change that. The ninth split a name with a backslash at the end of a line, which the shell deletes before it runs the command and the gate didn't. My fix deleted it everywhere, and the tenth round showed the shell doesn't after a `#`, so `cat README.md #\` with a send on the next line read as one harmless `cat`. Now the gate looks for names in both spellings and refuses any command that names one and has a backslash or newline at all, so it never has to copy the shell's rules. The eleventh round went back to the oldest code in the gate: when a command has an unmatched quote, like `# it's` in a comment, or ends in a lone backslash, the parser gives up, and the fallback for that only looked for five exact file names. A quote-split `send_em''ail.py` or a write into `checks/` walked past it. Now a command the gate can't parse gets every check the others get, on a rough split with the quotes taken out, and is refused if any of them fires. The twelfth round used the same stray quote against a different check: the one that spots globs and `$'...'` tracks quotes, and a `# it's` on line one made it think line two was quoted, so `hook?/json.py` or `chec$''ks/` on line two went unseen. It now reads the command with comments skipped, without, and line by line, and refuses if any reading finds one. The thirteenth round found my comment rule was still looser than the shell's: a `#` right after an escaped space (`true \ # ...`) is plain text to the shell, but the gate skipped the rest of the line as a comment, and `$1ail` read as one variable when the shell reads `$1` then `ail`. The variable one now reads the way the shell does. The fourteenth found two more places where my copy of the shell's comment rule was wrong, inside backticks and inside a nested `${...}`. That was the fourth round in a row to beat a copy of the shell's quoting rules, so I stopped copying them, the same call I made with shell syntax in round two: once a command has anything that makes quoting hard to read (a `#`, a backtick, `$(`, `${`, a heredoc or a second line), every glob character counts, quoted or not. The fifteenth round pointed out that the shell running these commands on a Mac is zsh, not bash, and zsh has glob patterns bash doesn't: `send_emai(l).py` is the sender to zsh, and the gate only knew `*`, `?`, `[..]` and braces. It also passed quoted globs handed to `bash -c` or `eval`, which expand them a second time. Both now count. The sixteenth got past that fix with a shell name the gate didn't spot because it was quoted or escaped (`'bash' -c`, `\eval`, `$SHELL -c`), and with zsh's `x#` split by quotes (`send_ema'i'#l.py`). Shell names are now matched with quotes and backslashes taken out, and any `$` the shell expands makes every glob count, quoted or not. The seventeenth found one more spelling: zsh turns `=bash` into `/bin/bash`, and the gate only looked for a shell name after a space or a few symbols, not after `=`. Now it does. Every bypass from all seventeen rounds is a test in [`tests/test_send_gate.py`](tests/test_send_gate.py).

## Run it

```bash
pip install pytest
python3 -m pytest -q            # 329 tests, every rule shown blocking, not just passing (Python 3.11+)
cp approvals.example.txt approvals.txt
mkdir -p .claude && cp examples/settings.json .claude/settings.json   # wire the hook into Claude Code
```

Then ask Claude Code in this folder to send an email with `examples/send_email.py`. The sender is a stub and never transmits. Try a recipient that isn't in `approvals.txt` and watch the hook refuse.

To see that the tests have teeth, make `decide()` in the gate return `None` (allow everything) and rerun: 282 tests fail.
